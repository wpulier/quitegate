# Phase 3b-3b-ios — Fold `MobileBlockingScreen` into `MobileTuningScreen` + drop the Blocking tab Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Reach the spec §3 IA on iOS — Tortoise's mobile tab bar becomes **Usage / Tune / Devices** and "Blocking" is no longer a separate tab; its two real controls (the access-mode selector and the 3b-2a locked-session card) live under the one **Tune** surface.

**Architecture:** This is the iOS half of the nav fold (the Mac half is already done: Mac is Devices/Tune/Usage, `ControlView` deleted). It is a pure IA/navigation move over controls that are already 100% real — **no new fake data, no new enforcement logic.** Every edit is in one file, `Tortoise/ContentView.swift`. Task 1 copies the mode selector + session card into `MobileTuningScreen` while `MobileBlockingScreen`/the Blocking tab is still live (both screens momentarily coherent, harmless file-scoped duplication of nothing — the moved code just references the same `screenTime` controller). Task 2 flips the navigation: drops `.blocking` from `MobileSection`, deletes `MobileBlockingScreen`, retargets the four `.blocking` references, and retitles Tune. The Tune screen already owns `screenTime` (which owns the whole session API), so the session card moves with zero new plumbing; the mode selector needs three new inputs threaded from the shell.

**Tech Stack:** Swift 5, SwiftUI, FamilyControls, UIKit.

## Global Constraints

- **No iOS unit-test target** — SwiftUI views are **build-verified only**. There is nothing to TDD here (the `MobileSection` enum is `private` inside the iOS-only `Tortoise/ContentView.swift`, not in the macOS `QuietGate` test target).
- **iOS builds are SLOW (~15-25 min).** Run `xcodebuild` via the **Bash tool ONLY** (never an Xcode/xcodebuild MCP tool — that has hung); **one build at a time, foreground**, let it finish.

- macOS suite: `xcodebuild -project QuietGate.xcodeproj -scheme QuietGate -configuration Debug -destination 'platform=macOS' -derivedDataPath build/DerivedData test`
- **One file, no `xcodegen`.** All edits are pure in-file view edits to an existing source file (`Tortoise/ContentView.swift` is already in the `Tortoise` target group); no file is created or deleted, so the project does **not** need regenerating.
- Product name **Tortoise**; minimal on-screen text; **NO fake/demo data reintroduced**; **all 3b-2a locked-session precommitment gates must remain intact** after the move.

## Confirmed iOS decisions (baked in — do not re-litigate)

1. **Three destinations: Usage / Tune / Devices.** iOS drops the Blocking tab; Usage stays a separate insight surface.
2. **iOS gets NO general Apps section and NO separate adult toggle.** iOS adult is mode-driven (Strict → Screen Time web filter); iOS targeting stays the Screen Time picker. So **only the mode selector + the real 3b-2a session card** move from Blocking into Tune. (This is the key difference from the Mac fold, which also moved adult/apps/websites.)
3. **No duplicate `MobileIOSYouTubeStatusCard` at Tune top level.** That card already renders inside `MobileTuningScreen` under the YouTube site — do **not** re-add it at the top of Tune.
4. **Keep ONE concise iPhone Screen-Time note.** The Blocking screen's single "On iPhone, blocks run through the Tortoise app and Screen Time…" `MobileCard` moves into Tune verbatim (placed with the session card). It does not duplicate any card already in Tune.
5. **Every locked-session gate moves verbatim.** Mode selector keeps `.disabled(isSyncing || screenTime.sessionLockedActive)`; every session button keeps `.disabled(screenTime.sessionLockedActive)`; the `sessionActive` / End-session / "Locked until it ends" logic is unchanged. Do not alter the session UI.
